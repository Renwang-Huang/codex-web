# Codex Web 项目质量与体验评估报告

> 历史审查材料，部分问题已修复，部分判断经核实不成立；当前结论见 [审查处理记录](../REVIEW_RESPONSE.md)。下文不代表当前版本的状态或独立验收结论。个人目录已替换为示例。

> 评估基准：Codex Web v0.1.0 · Node.js 24+ · Linux · 针对 Codex CLI 0.164.0
> 评估范围：架构设计、底层契约、安全模型、资源与性能、缺陷分析、用户体验与交互

---

## 1. 总体评价与质量评级

**综合评级：8.5 / 10（架构扎实、针对特定工程痛点设计克制的优秀自研系统）**

本项目不是一个玩具级的 WebUI 壳，而是一个针对 **多入口环境（`codex` / `codex1` / `codex2`）**、**跨终端（桌面/手机）** 且 **严格遵循底层 CLI 运行状态机制** 的严谨控制台。

### 核心设计亮点
1. **状态真值与安全下发模型（Ground Truth & No Blind Replay）**：
   - 彻底解耦了“Linux 进程存活”、“日志轮次事件”和“官方 WebSocket 连接”，不盲目把进程存活当成执行中。
   - 指令下发状态机严密（`pending` $\to$ `sending` $\to$ `sent` / `uncertain`），遇到断网或响应超时**决不自动重发**，防止破坏代码工作区或重复消耗 Token。
2. **原生持久队列集成（Native Queue Integration）**：
   - 巧妙利用 Codex CLI 0.164.0 的实验性原生队列接口（`thread/queue/add` / `delete` / `list`），对正在终端内运行的独立会话无需强行接管或 cold resume，即可安全排队后续指令由终端自行消费。
3. **安全边界与最小暴露原则**：
   - 本机采集端仅监听 `127.0.0.1:4317`，经加密反向 SSH 隧道暴露至公网入口；完整会话、私钥、本地操作保留在开发者机器。
   - 强化的 HTTP 响应头配置（严格 CSP、`HttpOnly` + `SameSite=Strict` Cookie、`Sec-Fetch-Site` 跨站隔离、IP 暴力破解频率限制）。
   - 没有通用 shell 执行或通用 JSON-RPC 透传端点，所有可写操作严格白名单化。
4. **自动化测试覆盖扎实**：
   - 包含 30 项全通的核心回归单元测试，以及基于 Playwright 的桌面/移动视口渲染测试、服务自愈回归（`relay-recovery.mjs`）和公网连通性验收。

## 2. 发现的缺陷与潜在技术隐患

### 2.1 【高危性能缺陷】SSE 触发 760KB 全量快照的高频“轮询风暴”
- **位置**：`server/hub.mjs` (L243-264)、`server/index.mjs` (L234-240)、`public/app.js` (L143)
- **原因机制**：
  1. 当 Codex 正在流式生成输出时，每个 Token Delta 都会触发 `this.emit("change")`。
  2. 服务端经过 250ms 防抖后，向浏览器广播空数据 SSE 事件：`event: change\ndata: {}\n\n`。
  3. 前端监听到 `change` 后不是拉取增量或局部更新，而是直接调用全量 `refresh()`，发起 `GET /api/snapshot`。
  4. 随着历史会话累积（当前已有 294 个会话），单次 `/api/snapshot` 的 JSON 报文高达 **~760 KB**。
- **实际影响**：
  在模型回答 20 秒的过程中，浏览器端每秒触发 3~4 次全量请求，累计拉取 **几十 MB 甚至上百 MB** 的重复 JSON。在手机 4G/5G 网络下不仅急速消耗流量，还会导致主线程高频 `JSON.parse`、卡顿、发热与掉电。

### 2.2 【资源空转损耗】无条件全量 `/proc` 扫描与磁盘递归
- **位置**：`server/discovery.mjs` (L23-40)、`server/sessions.mjs` (L153-165)
- **原因机制**：
  `hub.scan()` 每 4 秒无条件轮询一次：
  1. 遍历系统 `/proc` 下的所有 PID 并读取 `/proc/${pid}/status`、`/exe`、`/fd`。
  2. 递归遍历 3 个 home 下的 `sessions` 和 `archived_sessions` 目录（300+ 文件调用 `stat`）。
- **实测证据**：
  后台常驻服务 `codex-web.service` 在运行 23 小时后，空转累积 CPU 达到 **23 分钟**，内存占用达 **248 MB**。
- **实际影响**：
  增加了常驻主机的电量与 I/O 开销；且 `SessionIndex.cache` 缺乏 LRU 或失效驱逐逻辑，文件即使被清理也仍驻留内存。

### 2.3 【数据无界增长】`.local/state.json` 指令历史无生命周期淘汰
- **位置**：`server/hub.mjs` (L498)、`server/store.mjs` (L28-38)
- **原因机制**：
  所有发送的指令不断 `push` 进 `store.data.commands`，从未执行清理或截断。
- **实际影响**：
  每次扫描计算会话队列（`queuedCount`）、每次打开详情、每次写入都要遍历全量历史指令，磁盘持久化文件体积单调递增。

### 2.4 【快捷键并发防抖缺失】`Ctrl+Enter` 触发 409 报错
- **位置**：`public/app.js` (L346-350, L396-405)
- **原因机制**：
  在输入框按快捷键发送时调用 `$("#composer").requestSubmit()`。虽然按钮在提交后设置了 `button.disabled = true`，但原生 `form.requestSubmit()` **不会校验按钮是否 disabled**。
- **实际影响**：
  若用户连续敲击两次 `Ctrl+Enter`，第二次请求会生成新的 `requestId` 并发向后端发起请求，触发后端的锁返回 `409 CONFLICT`，导致界面弹出突兀的错误提示（*“该会话有指令正在发送，请稍后再试”*）。

### 2.5 【消息去重逻辑导致同名回复丢失】
- **位置**：`server/hub.mjs` (L380-394)
- **原因机制**：
  从官方 `thread/turns/list` 同步轮次消息时，使用了 `!messages.some((m) => m.text === it.text)` 进行全量查重。
- **实际影响**：
  如果助手在不同轮次给出了相同或简短回复（如“好的”、“已完成”、“收到”），后续轮次的回复会被当作“已存在”而**直接被静默丢弃**。且该合并逻辑遗漏了 `userMessage`。

### 2.6 【登出 Cookie 清除不完全】
- **位置**：`server/index.mjs` (L145-150)
- **原因机制**：
  `/api/logout` 下发的清除 Cookie 头未添加 `Secure` 属性。根据 RFC 6265bis 规范，在 HTTPS 下由 `Secure` 标记设置的 Cookie 无法被无 `Secure` 标记的 `Set-Cookie` 清除。

### 2.7 【审计日志遗漏核心认证事件】
- **位置**：`server/index.mjs` (L112-134)
- **原因机制**：
  `/api/login` 在验证成功后直接 `return json(...)`，未进入 `audit.jsonl` 的写入流程。
- **实际影响**：
  密码错误尝试、暴力破解拦截、以及合法登录记录均未记录在审计日志中。

## 3. 影响用户体验的问题 (UX Friction Points)

| 体验痛点 | 问题现象 | 用户影响 |
| :--- | :--- | :--- |
| **无 Markdown 与代码高亮** | 回复直接渲染在 `.message-text`，仅依赖 CSS `white-space: pre-wrap;` 显示纯文本。 | 代码块、Diff、加粗、列表没有结构化排版和语法着色，程序员查看长代码或排查补丁时阅读体验较差。 |
| **缺少一键“复制”功能** | 没有为代码块、助手最终结果提供“复制”图标/按钮。 | 在手机端查看结果时，必须手动长按选区滑动拖拽复制，容易误选时间戳或触发手机手势。 |
| **移动端侧滑/后退导致退出页面** | 移动端进入详情页仅通过切换 `.mobile-detail` 类名，未接入浏览器历史栈（`history.pushState` 或 `location.hash`）。 | 手机用户侧滑返回或按系统“返回键”时，**会直接退出页面**而非回到会话列表；页面一旦刷新，选中状态直接丢失。 |
| **输入框未自适应高度** | 下发指令的输入框固定为 3 行（`rows="3"`）。 | 粘贴多行指令或需求时出现细小纵向滚动条，移动端调起虚拟键盘后视口局促。 |
| **缺乏暗色模式（Dark Mode）** | 仅有一套偏亮绿色的浅色主题。 | 夜间在移动设备或暗色 IDE 环境中监控会话时十分刺眼。 |
| **会话无法重命名** | 会话标题永久取自首次 Prompt 截断的前 90 个字。 | 无法为重要会话设置自定义别名（如“重构验证”、“紧急补丁”）。 |
| **新建会话需手动输入绝对路径** | 新建表单要求用户手打 `/home/user/...` 绝对路径。 | 缺少常用/历史目录下拉建议，在手机端输入容易输错。 |
| **移动端息屏唤醒数据滞后** | 缺少对 `visibilitychange` 事件的监听。 | 手机息屏切回浏览器后，前端停留在陈旧快照，必须等待轮询定时器触发才更新。 |
| **Token / 上下文消耗未呈现** | 后台在日志中解析了 `tokenUsage`，但界面完全隐藏。 | 用户无法感知当前会话的上下文饱和度及模型用量。 |

## 4. 改进路线与建议

### 阶段一：核心稳定性与流量优化（高优先级）
1. **重构 SSE 推送粒度（解决 760KB 风暴）**：
   - 服务端广播具体事件元数据（例如 `{ type: "turn_delta", key, delta }`、`{ type: "state_change", key }`）。
   - 前端根据事件更新当前选中会话，或仅拉取单会话的增量 `detail`，避免全量轮询 `snapshot`。
2. **前端提交防抖**：
   - 在表单提交逻辑增加 `isSubmitting` 锁，避免快捷键并发下发产生 409。
3. **修复消息去重逻辑**：
   - 使用 `turnId + messageIndex` 或相邻指针替代全量 `some(m => m.text === text)`。
4. **清理历史指令**：
   - 对 `state.json` 中的已完成/取消指令引入保留上限（如保留最近 100 条）。

### 阶段二：人机交互与体验升级（中优先级）
1. **引入轻量 Markdown 格式化与一键复制**：
   - 对助手输出做基础代码块提取（带语言标记与一键复制按钮）。
2. **移动端哈希路由适配**：
   - 点击会话时修改 `window.location.hash = s.key`，监听 `window.onpopstate`，支持自然的屏幕侧滑返回。
3. **交互细节润色**：
   - 输入框增加自适应高度支持。
   - 监听 `visibilitychange`，在页面重新可见时静默触发一次状态核对。
   - 增加浅色/深色主题适配（`prefers-color-scheme: dark`）。
